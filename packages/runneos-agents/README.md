# RunneOS Agents

Постоянные ИИ-агенты на своей машине: у каждого своё имя, своя роль, свой воркспейс и свой журнал.
Задачи выполняются через уже установленные и оплаченные CLI-провайдеры (`codex`, `opencode`),
без собственного облачного сервиса и без передачи ключей третьей стороне.

Пакет входит в RunneOS как отдельный компонент: рабочий стол, вход и обновления ОС работают
и без него. Если провайдера нет, `runneos-agents` честно говорит об этом и не выполняет задачу.

## Зачем свой, если есть похожие

- **openbot.run** (nightly-labs/openbot) понравился формой работы, но его лицензия — PolyForm
  Noncommercial 1.0.0, то есть не свободная: коммерческое использование и распространение
  ограничены. В RunneOS такой компонент недопустим. Отдельно: до тега v0.1.11 тот проект
  выходил под Apache-2.0 — это зафиксировано в лицензионном отчёте, но мы не берём чужой код.
- **CopilotKit/OpenBot** — MIT, но обязательным компонентом идёт CopilotKit Intelligence: без
  `INTELLIGENCE_API_KEY` сервер не стартует. Проверяемые факты: локальная evaluation-лицензия
  длится 30 дней и продлевается (`npx copilotkit@latest local renew`), локальная оценка
  официально поддержана только на macOS (для Linux — «has not been verified»), а
  продакшн-самохостинг (VPC/On-Prem) — платный план. **Лицензионный статус самой Intelligence
  не проверен**: текста её лицензии в открытом доступе нет, поэтому «несвободная» — не факт, а
  предположение. Итог для нас не меняется: такой control plane требует внешнего аккаунта и
  периодического интернета, а нам нужна работа без него.
- Поэтому здесь **своё ядро** (MIT): журнал событий в SQLite, воркспейс на агента, адаптеры
  к CLI. Идеи взяты как идеи, код — свой. Разбор лицензий:
  [docs/research/2026-10-12-agent-workspace-foundations.md](../../docs/research/2026-10-12-agent-workspace-foundations.md).

## Установка и первый запуск

```sh
# пакет из репозитория RunneOS
sudo pacman -S runneos-agents

# данные и база в ~/.local/share/runneos/agents
runneos-agents init

# кто вообще доступен как провайдер
runneos-agents provider list

# агент и его воркспейс
runneos-agents agent add reviewer --role 'проверяю патчи и отчёты'

# задача агенту
runneos-agents ask reviewer 'посмотри README и предложи три улучшения'
```

Из графики: `runneos-agents-panel` (GTK4/libadwaita) — список агентов, сессии, лента сообщений
и поле задачи.

### Виджет на панели DMS

Пакет кладёт источник виджета в `/usr/share/dms-plugins/RunneosAgents/`, но DMS оттуда его
автоматически не читает. По проверке установленных плагинов и бинаря `dms-shell 1.6.3-2`
оболочка берёт плагины из `~/.config/DankMaterialShell/plugins/<id>/`. (В QML внутри бинаря
есть также системный путь `/etc/xdg/quickshell/dms-plugins`; на этой машине такого каталога
нет, и читает ли DMS плагины оттуда — независимо не проверено.) Установка — скопировать
каталог целиком и перезагрузить оболочку:

```sh
mkdir -p ~/.config/DankMaterialShell/plugins
cp -r /usr/share/dms-plugins/RunneosAgents ~/.config/DankMaterialShell/plugins/
# затем перезагрузить оболочку DMS (например: dms restart) или выйти и войти в сеанс
```

`plugin.json` объявляет `id: "runneosAgents"` и `component: "./RunneAgentsWidget.qml"` — этот же
`pluginId` стоит в самом виджете, менять их по отдельности нельзя. Виджет показывает состояние
агентов и последнюю строку, по клику открывает панель; данные берёт только из `runneos-agents
... --json`, в SQLite и сеть не ходит. **В живой DMS виджет пока не загружался.** Проверено
машиной: `/usr/lib/qt6/bin/qmllint` (полный путь: в `PATH` этого бинаря нет) — 0 ошибок; при
прямом вызове без путей импорта он даёт 21 предупреждение, и все они про
`import`/`unresolved-type`/`unqualified` для модулей `qs.*` (пути импорта Quickshell/DMS в
репозитории не заданы). Зафиксированный исполнителем результат «0 ошибок и 0 предупреждений»
получен с этими путями импорта и здесь не воспроизводится. Соответствие
`plugin.json` ↔ `pluginId` ↔ `PKGBUILD` проверяется тестом `tests/test_agents_panel.py`. Разовый
разбор логики виджета в Node (55 проверок) делался вне репозитория и **не воспроизводится**:
harness в репозиторий не положен.

## Команды

| Команда | Что делает |
|---|---|
| `init` | создаёт корень данных, базу и каталоги |
| `provider list` | доступность провайдеров и причина, если недоступен |
| `agent add NAME [--role TEXT] [--provider codex] [--id SLUG]` | создать или обновить агента |
| `agent list` / `agent show ID` / `agent remove ID` | список, подробности, удаление из базы |
| `ask ID PROMPT [--new] [--session ID] [--model M] [--timeout S]` | задача агенту |
| `sessions ID` | сессии агента |
| `log SESSION_ID [--after SEQ]` | журнал событий сессии |
| `doctor` | проверки без изменений: корень, база, воркспейсы, провайдеры |

`--json` понимается и до, и после подкоманды: вывод — по одному JSON-объекту на строку.
Коды возврата: `0` успех, `1` ошибка выполнения, `2` неверное использование.
Отсутствие провайдера — код `1` и человекочитаемая причина, без трассировки.

## Где лежат данные

```
$XDG_DATA_HOME/runneos/agents/          (по умолчанию ~/.local/share/runneos/agents)
├── agents.db        # агенты, сессии, сообщения, журнал событий (SQLite, WAL)
├── workspaces/<id>/ # воркспейс агента: его файлы, agent.json, локальный git
│   └── runs/<session>.jsonl   # журнал прогона: по строке на событие, пишет оркестратор
└── runs/            # создаётся `init`, но ничем не наполняется: журналы лежат в воркспейсах
```

Журнал прогона — `<workspace>/runs/<session>.jsonl` рядом с работой агента, а не в корне данных.
Источник правды — база; файл нужен, чтобы открыть историю прогона без SQLite. Запись невозможна
(нет прав, диск) — прогон продолжается: журнал это удобство, а не условие работы.

Переопределение корня: `RUNNEOS_AGENTS_HOME=/путь`. Тесты используют временный корень.

## Если провайдера нет (и почему ОС от него не зависит)

Пакет не запускает ничего сам: ни службы, ни таймера, ни автозапуска при входе. Провайдер —
обычная внешняя программа, и её отсутствие — штатное состояние, а не поломка системы:

```sh
$ runneos-agents provider list
codex      недоступен · бинарь codex не найден: его нет в PATH и в стандартных каталогах (~/.local/bin, /usr/local/bin, /usr/bin)
opencode   недоступен · бинарь opencode не найден: …

$ runneos-agents ask reviewer 'ответь ровно PONG'
ошибка: бинарь codex не найден: …            # код возврата 1, строки Traceback нет
```

При этом: задача **не запускается**, агент переходит в состояние `unavailable`, в журнале
остаются `user_message` и `error` с причиной, содержимое воркспейса не меняется. Рабочий стол,
вход, сеть и обновления работают как обычно — пакет не является их зависимостью и не входит в
сеанс. То же и с графикой: панель без ядра показывает «Ядро runneos_agents не найдено», виджет
без CLI — «Агенты · недоступны»; ничего не падает и не блокирует оболочку.

Проверка этого состояния на машине (провайдеры временно убраны из `~/.local/bin`, затем
возвращены; данные — во временном корне): [docs/results-agents-2026-10-12.md](../../docs/results-agents-2026-10-12.md),
раздел 2.7; архитектура и режимы отказа: [docs/agents-architecture.md](../../docs/agents-architecture.md).

## Что реализовано, а что нет

Реализовано (первый срез, 2026-10-12):

- агенты с собственным воркспейсом и манифестом;
- сессии с продолжением у провайдера (`codex exec resume`) и явным `--new`;
- журнал событий как источник правды: каждое событие сначала в базу, потом в интерфейс;
- адаптер Codex CLI (JSONL: `thread.started`, `item.completed`, `turn.completed`, usage);
- адаптер opencode: подтверждённый неинтерактивный `opencode run --standalone --format json`
  (живой прогон opencode v2.0.26, фикстуры сняты с него), продолжение по `--session`;
- честная недоступность провайдера: причина, состояние `unavailable`, задача не запускается;
- CLI и GTK4-панель, `doctor` без изменений в системе.

Пока нет (следующие срезы, не «сделано»):

- межагентные каналы и передача задач между агентами;
- песочница уровня ОС (bubblewrap/systemd-run, лимиты cgroup) — не реализована. codex при этом
  запускается со своей песочницей записи (`-s workspace-write` для нового хода и
  `-c sandbox_mode=workspace-write` для resume), но воркспейс агента остаётся договорённостью
  и рабочей областью, а не барьером;
- политики доступа: модуль `policy.py` есть, но **к рантайму не подключен** — ни оркестратор,
  ни адаптеры, ни CLI, ни панель его не вызывают, поэтому правила не применяются ни к чему;
- расписания (routines), уведомления, работа нескольких провайдеров одновременно;
- собственный API/сокет: сейчас CLI и панель работают через прямое подключение к базе;
- автоодобрение прав `opencode`: адаптер запускает `opencode run --standalone --format json`
  без флага `--auto`, поэтому задача, требующая подтверждения прав, упрётся в таймаут.

## Ограничения и безопасность

- **Секреты не хранятся пакетом.** Авторизацию провайдера держит его собственный CLI
  (например `~/.codex`). Пакет не читает и не копирует эти данные.
- **Редакция секретов: строгость разная по месту.** В файловом журнале прогона
  (`<workspace>/runs/<session>.jsonl`) значения ключей вида
  `*_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD`/`*_CREDENTIAL`/`*_AUTH` заменяются, длинные строки
  обрезаются (`_sanitize_payload` в оркестраторе). В SQLite payload события пишется как есть, без
  такой замены по именам ключей: секреты вырезаются только **по значению** — те, что нашли
  адаптеры (значения переменных окружения с секретными именами и узнаваемые формы токенов).
  Кроме вывода провайдера в базу пишутся текст задачи пользователя (`user_message`) и системные
  сообщения с причинами отказов, так что «в базу идёт только то, что вернул адаптер» — неверно.
  Окружение процесса в отчёты не пишется.
- **Точка расширения `RUNNEOS_AGENTS_ADAPTER_PATH`.** Если переменная задана, ядро
  (`routing.py`) импортирует указанный Python-файл и вызывает в нём `build_registry()` — так
  тесты подменяют адаптеры, так же могут подключаться внешние провайдеры. Риск: это исполнение
  произвольного Python-кода из указанного пути с правами пользователя. Не задавайте переменную
  без необходимости и указывайте только файл, которому доверяете.
- **Удаление агента** убирает его из базы вместе с сессиями и журналом; файлы воркспейса
  намеренно остаются — их удаляет человек.
- **Подписки.** Задачи идут от вашего имени через ваш CLI. Условия подписки — ваша
  ответственность; пакет не обходит ограничения провайдера и не перепродаёт доступ.
